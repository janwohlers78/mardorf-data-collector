# WP13 prepared collector

One inactive collector package serves observations, deterministic GRIB and full ensembles. `core_v1` owns configured jobs, budgets and transfer envelopes; `adapters_v1` retains provider-native fields and extraction metadata; `store_v1` owns immutable local delivery; `history_v1` owns bounded, resumable historical jobs and the existing CLI's offline preparation command. One contract bundle pins the private WP12 V2 source. The existing validation workflow installs an optional hashed native GRIB lock; no collection workflow is added.

Jobs require explicit profile, sites, provider, sensor/station (observations), model/product/run expectations (forecasts), source URL/encoding/role, targets and history bounds. No site coordinate is embedded in generic code. Two configured sites use the same raw GRIB download and distinct actual nearest-grid extractions. Full raw bytes and unknown provider fields remain retained. Native metadata keeps model run, observation clock, interval, units, roles and actual coordinates separate; it does not infer missing publication clocks.

Offline entrypoint: `python -m mardorf_collector wp13-prepare --job JOB.json --responses RESPONSES.json --output DIRECTORY`. Each response specifies a local file path, original UTC capture and HTTP status. The manifest and receipt hashes support immutable readback; successful empty results retain raw bytes. Failed sources or incomplete/inconsistent ensembles cannot produce a transfer envelope.

Historical API: `history_manifest` followed by `run_history`, with an explicit source cache, delivery root and manifest path. Each invocation handles at most eight requests and eight windows, three attempts per window, 30 seconds and the pinned WP12 byte/RSS budgets. Resume requires contiguous, hash-verified window receipts. Cache reuse preserves the original capture clock; a new `refresh_id` is needed to retry a successful HTTP response with invalid native content. An injected transport is a preparation/test interface; default network collection is disabled by the release contract.

`config/dev03_wp13_collector_release_v1.json` pins source/config/fixture bytes, consumer capabilities, limitations and an owner/gate-based legacy retirement ledger. WP14 must deploy and prove the consumer before WP15's real canary and explicit activation. There is no additional forecast service, no calibration fit and no operational authority change.
